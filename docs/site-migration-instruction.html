Перенос сайта через Cursor

Инструкция для веб-разработчиков: как переносить сайт с конструктора или другой CMS на новый проект (чаще всего WordPress) с помощью Cursor.

Опыт взят с реальных переносов: Tilda → WordPress и Tilda → WordPress + WooCommerce. Подход тот же, если источник — другой конструктор, CMS или самопис.

1. Главная идея переноса

Мы не копируем код старого сайта (Tilda, конструктор, чужая тема CMS) «как есть». Мы заново верстаем блоки так, чтобы внешне и по поведению сайт был один в один с оригиналом, но код был чистый и поддерживаемый.

  • Источник — эталон по виду, контенту, анимациям, адаптиву.
  • Новый проект — чистая вёрстка (БЭМ), нормальная тема/шаблоны целевой CMS, локальные картинки и скрипты.
  • Сквозные блоки (шапка, футер, повторяющиеся секции) — в отдельных файлах и подключаются везде одинаково.
  • Одинаковые по структуре страницы — через шаблоны.
  • Статичный контент по возможности — через админку целевой CMS (страницы, поля), а не захардкоженным текстом.

Коротко: вид 1 в 1, код — новый.

2. Что подготовить до чата

Обязательно

  • URL исходного сайта (эталон).
  • URL тестового/нового сайта (куда переносим).
  • Понимание целевой платформы: WordPress, WordPress + WooCommerce, Bitrix, чистый HTML и т.д.
  • Список страниц к переносу (sitemap, выгрузка URL, или «весь сайт»).
  • Доступы к тестовому сайту держите под рукой, но не вставляйте их в первый промпт. Сначала план и вопросы — доступы только после согласования плана (см. раздел про доступы).
  • В корне проекта уже лежат настройки Cursor: AGENTS.md, .cursorignore, папка .cursor/ (запросить у руководителя, если нет).

Желательно заранее решить

  • Формы: переносим / делаем через готовый модуль (например exform) / оставляем заглушки и список страниц с формами.
  • Меню: через стандартное меню CMS (предпочтительно) или временно в шаблоне.
  • Аналитика и cookie-баннер: переносим или нет.
  • Шрифты: только свободные (часто Google Fonts); если точного нет — ближайший аналог.
  • Интернет-магазин: переносим ли товары/категории или только стилизуем шаблоны + демо-товары.
  • Нужны ли ACF / произвольные поля, Classic Editor и т.п.

Режим в Cursor

  1. Новый чат на весь перенос (или отдельный чат на крупный этап).
  2. Сначала режим Plan — план и вопросы без паролей.
  3. После согласования плана — отдельным сообщением доступы к тесту, затем «начинай».
  4. Дальше режим Agent (или Build в Plan).
  5. Модель: для плана и сложного переноса можно взять помощнее; на мелкие правки после эталона — Auto, чтобы не жечь лимит.

3. Порядок работы

Не пытайтесь перенести «весь сайт за один заход без сверки». Рабочий порядок такой:

  1. План. Отправьте универсальный промпт (раздел 7) без паролей. Агент задаёт вопросы — отвечаете коротко и по делу.
  2. Доступы. Когда план согласован и вы готовы начинать реализацию — передайте доступы к тестовому сайту отдельным сообщением (см. раздел про доступы). Затем напишите «начинай».
  3. Аудит эталона. Список страниц, блоки главной, шрифты, сквозные части, формы, скрипты аналитики. Ничего не выдумывать — только то, что видно на исходном сайте.
  4. Каркас целевого проекта. Тема/шаблоны с нормальным набором функций CMS (чтобы плагины не ломались). Без подключения ресурсов со старого CDN.
  5. Шапка, меню, футер. Сначала сквозные части. Меню — через стандартный функционал CMS, стили как на эталоне.
  6. Главная. Доводите до 1 в 1 поблочно. Несколько проходов сравнения. Пока главная, шапка, меню и футер не ок — внутренние страницы не трогать массово.
  7. Шаблоны и остальные страницы. Одинаковые блоки вынести в файлы. Контент — в админку, где возможно. URL — по согласованному списку/sitemap.
  8. Особые разделы. Каталог WooCommerce, формы, cookie, метрика, микроразметка — по брифу.
  9. Финальные итерации. Пройтись по всем URL эталона vs теста. Убрать лишнее, чего нет на оригинале (крошки, лишние page-title блоки, «Made on Tilda» и т.п.).

4. Когда и как передавать доступы к тестовому сайту

На каком этапе

  1. Сначала отправьте универсальный промпт без логинов и паролей — только URL эталона, URL теста, платформа, объём работ, формы, меню и остальные решения по брифу.
  2. Дождитесь плана и ответьте на уточняющие вопросы агента.
  3. Когда план вас устраивает — отдельным сообщением передайте доступы к тестовому сайту.
  4. После этого напишите «начинай» / «начинай реализацию».

Доступы нужны агенту уже для заливки темы, правок на сервере и проверки теста. До согласования плана пароли в чат не кладём — меньше риска утечки и случайной правки «не туда».

Какие доступы обычно нужны

  • Админка CMS: URL входа, логин, пароль (или отдельный тестовый пользователь с нужными правами).
  • FTP или SFTP: хост, порт, логин, пароль, путь к корню сайта или к wp-content / шаблонам.
  • При необходимости — данные БД (хост, имя базы, пользователь, пароль, префикс таблиц). Часто достаточно того, что уже есть в конфиге на сервере; отдельно передавайте только если без этого не обойтись.

Доступы к эталону (боевой Tilda/старый сайт) обычно не нужны, если сайт открыт публично. Если эталон закрыт паролем — согласуйте с руководителем отдельный просмотрный доступ.

Как вставить доступы правильно и безопасно

  • Берите доступы у руководителя (или из принятого в компании безопасного хранилища). Не пересылайте пароли в общий рабочий чат команды «на всякий случай».
  • Вставляйте доступы только в тот чат Cursor, где идёт этот перенос, и только когда план уже согласован.
  • Пишите доступы отдельным сообщением, структурировано по пунктам — так меньше ошибок при копировании:

Хост:

Пароль:
Путь к сайту / wp-content:

3. БД (если нужна отдельно)
Хост:

На эталон и другие проекты эти доступы не применять.
После получения доступов начинай реализацию по плану.
  • Передавайте только тестовые доступы. Боевой (прод) сервер в чат для переноса не даём, если задача явно не про прод.
  • Не вставляйте пароли в файлы проекта, в README, в правила Cursor, в скриншоты для клиента и в git.
  • Не просите агента сохранять пароли в репозиторий или в открытый файл темы.
  • Если пароль уже засветился не туда — сразу напишите руководителю: лучше сменить пароль на тесте.
  • После окончания переноса доступы в чате не «размножайте»: не копируйте тот же блок в новые чаты без нужды.

Чего не делать

  • Не класть пароли в первый большой промпт вместе с брифом.
  • Не писать доступы одной длинной строкой без подписей — легко перепутать логин FTP и логин админки.
  • Не давать доступы от эталона/прода «на будущее».
  • Не вставлять пароли в комментарии к коду и в коммиты.

5. Правила, которые нельзя нарушать

  • Не переносить «мусор» конструктора/старой темы. Не копировать HTML блока со старого сайта и не вставлять как есть.
  • Не подключать стили, скрипты и картинки с CDN/хоста старого сайта. Всё скачать и положить в новый проект локально.
  • Не выдумывать страницы, классы, поля ACF, шаблоны WooCommerce и пути темы. Сначала смотреть реальный эталон и реальные файлы проекта.
  • Вёрстка: БЭМ (или схема имён проекта), семантика HTML5, адаптив, базовая доступность, поддерживаемый код.
  • Одинаковые блоки — сквозные файлы, подключение в шаблонах.
  • Главная — обычно отдельный шаблон. Простые статичные страницы — через страницы CMS + контент в админке.
  • Тема WordPress должна содержать стандартный набор файлов и функций темы, чтобы сторонние плагины работали предсказуемо.
  • Для WooCommerce править только нужные шаблоны через папку woocommerce в теме (overrides), не ломая ядро плагина.
  • Не добавлять на новый сайт служебные подписи конструктора («Made on Tilda» и аналоги).
  • Не оставлять на внутренних страницах типичный «WP-мусор», которого нет на эталоне: лишние хлебные крошки, навигацию разделов над заголовком, чужой фон и т.д.

6. Как сравнивать и доводить до 1 в 1

  1. Откройте эталон и тестовый сайт рядом (два окна / две вкладки).
  2. Сравнивайте поблочно: шапка → каждый блок главной → футер.
  3. Смотрите не только «похоже», а конкретно: отступы, ширина контейнера, шрифты, цвета, hover, sticky, мобильное меню, слайдеры, аккордеоны.
  4. Пишите агенту короткий баг-лист пунктами — так правки точнее, чем «сделай лучше».
  5. После серии фиксов просите ещё 2–3 прохода по той же странице. Агент часто считает задачу закрытой раньше времени.
  6. Когда шапка, меню, футер и главная приняты — явно напишите: «главную, шапку и футер больше не трогаем» и переходите к остальным страницам.
  7. На внутренних страницах снова сравнивайте с эталоном URL за URL, а не «по памяти».

Формулировка, которая хорошо работает:

Сравни с эталоном поблочно. Различий быть не должно. Не выдумывай — смотри стили и структуру на исходном сайте. Сделай несколько итераций, пока не будет 1 в 1.

7. Типовые ошибки агента

Что часто ломается Как реагировать
Вёрстка «на глаз», не как на эталоне «Не выдумывай. Открой эталон, сними стили/структуру и повтори»
Картинки с CDN старого сайта или битые пути «Скачай локально, положи в тему/uploads, подключи оттуда»
Меню хардкодом «Сделай через стандартное меню CMS, стили оставь 1 в 1»
Лишние крошки, page header, тёмный фон «На эталоне этого нет — убери»
Нет анимаций/слайдера/аккордеона Указать конкретный блок и поведение на оригинале
Футер/шапка разъехались после правок внутренних «Шапка и футер уже приняты — не меняй, только эта страница»
Формы забыты Либо подключить модуль форм, либо оставить заглушку и список страниц
«Готово», а страницы ещё отличаются «Не завершай. Пройди все URL из списка ещё N раз»

8. Универсальный промпт для переноса

Скопируйте в новый чат (режим Plan). Подставьте свои URL и ответы в квадратных скобках.

Пароли в этот промпт не вставляйте. Сначала план и вопросы. Доступы — отдельным сообщением после согласования плана (см. раздел про доступы).

Давай составим полный план действий. Если что-то непонятно — задай вопросы, не додумывай.

Ты — веб-разработчик. Задача: перенести сайт с [ИСТОЧНИК: Tilda / другой конструктор / CMS / самопис] на [ЦЕЛЬ: WordPress / WordPress+WooCommerce / Bitrix / HTML].

Эталон (основной сайт): [URL_ЭТАЛОНА]
Куда переносим (тест): [URL_ТЕСТА]

Цель результата:
- тестовый сайт выглядит и ведёт себя 1 в 1 как эталон: контент, вид, функционал, эффекты, адаптив;
- переносим [весь сайт / список страниц: …];
- код источника НЕ копируем и не переносим «мусор» конструктора/старой темы;
- каждый блок верстаем заново, но визуально и по поведению — 1 в 1.

Требования к коду:
- чистый, читаемый, поддерживаемый код;
- методология БЭМ (если в проекте уже другая строгая схема имён — следуй ей и скажи об этом);
- семантическая вёрстка, HTML5/CSS3;
- адаптив и кроссбраузерность для современных браузеров;
- базовая доступность;
- SEO-аккуратная разметка;
- ничего не выдумывать: только реальный эталон и реальные файлы целевого проекта.

Ассеты:
- не подключать стили/скрипты/изображения с хоста или CDN источника;
- всё нужное скачать и разместить локально в новом проекте, затем подключить оттуда.

Шрифты:
- только свободные шрифты (предпочтительно Google Fonts);
- если на эталоне шрифт есть в Google Fonts — использовать его;
- если точного нет — ближайший свободный аналог (согласовать).

Сквозные блоки и шаблоны:
- повторяющиеся блоки выносить в отдельные файлы и подключать в шаблонах;
- для страниц с одинаковой структурой — шаблоны;
- главную реализовать в шаблоне;
- простые статичные страницы — через стандартные страницы CMS и контент в админке, где это возможно.

[Если WordPress:]
- тема должна содержать стандартный набор файлов и функций темы, чтобы плагины работали нормально;
- меню — через стандартные меню WordPress, стилизация всех уровней 1 в 1 с эталоном;
- при наличии Classic Editor и ACF — использовать их по назначению (контент в админке, сложные поля через ACF).

[Если WooCommerce:]
- стилизовать шаблоны магазина через overrides в папке woocommerce темы;
- массово товары/категории [не переносим / переносим];
- для теста создать [N] демо-товаров/категорий;
- страница каталога: [URL].

[Если Bitrix / другая CMS / HTML:]
- править только реальные шаблоны/компоненты проекта;
- ядро CMS не трогать;
- повторить принятую в проекте схему шаблонов.

Формы:
- [вариант A: не переносим логику, оставляем вёрстку/заглушки и в конце даём список страниц с формами]
- [вариант B: подключаем существующий модуль … и стилизуем под эталон]
- [вариант C: иное — описать]

Прочее:
- cookie-баннер: [нужен / не нужен]
- аналитика (Метрика/GA): [переносим коды / не переносим]
- микроразметка schema.org: [нужна / не нужна]
- комментарии в сложных местах шаблонов — на русском, коротко

Порядок работы:
1) сначала полный план и вопросы;
2) аудит эталона;
3) каркас темы/шаблонов;
4) шапка, меню, футер;
5) главная до состояния 1 в 1 (несколько итераций сравнения);
6) остальные страницы/шаблоны;
7) формы, аналитика и согласованные допы;
8) финальный проход по всем URL.

Оцени задачу и скажи, сможешь ли реализовать. Пока я не скажу «начинай» — код не пиши, только план и вопросы.
Доступы к тестовому сайту пришлю отдельным сообщением после согласования плана.

10. Чеклист сдачи

  • Все согласованные URL открываются на тесте.
  • Шапка, меню (все уровни), футер — 1 в 1 с эталоном, в том числе мобилка.
  • Главная и ключевые внутренние — поблочно сверены.
