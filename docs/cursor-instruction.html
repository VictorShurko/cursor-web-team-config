1. Установка, аккаунт и лимиты

Что такое Cursor простыми словами

Cursor — это редактор кода. Если вы работали в VS Code, будет знакомо. Главное отличие: рядом есть помощник, которому можно написать задачу обычным текстом. Он открывает файлы сайта, правит вёрстку, меняет тексты, помогает с переносом страниц.

Ваша роль не меняется: вы ставите задачу, смотрите результат и решаете, принимать правки или нет. Программа не сдаёт сайт за вас.

Аккаунт и доступы

Отдельный аккаунт заводить не нужно — рабочий аккаунт Cursor уже есть. Логин и пароль (или способ входа) запрашивайте у своего руководителя.

Cursor используем только по рабочим задачам. Для личных дел его не берём: на тарифе есть лимиты, и лишний расход быстро сажает общий бюджет команды.

Правила пользования общим аккаунтом

  • Не меняйте пароль и настройки аккаунта без согласования с руководителем.
  • Не передавайте доступы коллегам «мимо» руководителя и не пишите их в чаты и мессенджеры.
  • Не удаляйте чужие чаты и не ломайте общие настройки.
  • Не используйте аккаунт для личных проектов и экспериментов.

Установка

  1. Зайдите на сайт cursor.com и скачайте версию для своей системы (Windows или macOS).
  2. Установите программу как обычное приложение.
  3. Откройте Cursor и войдите в рабочий аккаунт, доступы к которому вы получили у руководителя.

Модели и расход лимитов

В чате можно выбрать разные модели. Переключатель — вверху окна чата (выпадающий список с названием модели).

  • Auto — режим по умолчанию для обычной работы. Его достаточно для большинства задач.
  • Более мощные модели — только для сложных случаев: запутанный баг, большой перенос, неочевидная логика в CMS, когда Auto не справился.

Примеры простых задач, где не нужна «тяжёлая» модель: правка текста, мелкий CSS, замена картинки, найти файл, сверстать несложный блок.

Если на каждую мелочь включать самую мощную модель, лимит заканчивается очень быстро. В итоге его может не хватить всей команде до конца периода.

Не уверены, какую модель выбрать — спросите у руководителя или у коллеги, который уже работает в Cursor.

Первый запуск

  1. Через меню File → Open Folder откройте папку сайта (не один файл, а всю папку проекта).
  2. Подождите немного: программа просматривает файлы проекта.
  3. Откройте чат с помощником сочетанием клавиш Ctrl + I (на Mac — Cmd + I).
  4. Напишите, например: «Кратко расскажи, что это за сайт и какие основные папки есть».

Если ответ в целом совпадает с тем, что вы знаете о проекте — всё работает нормально.

Настройки проекта

Для работы в Cursor на сайте нужны служебные файлы команды. Их не создаём сами — запрашиваем у руководителя (или берём из репозитория https://github.com/VictorShurko/cursor-web-team-config по указанию руководителя):

  • файл .cursorignore;
  • файл AGENTS.md;
  • папку .cursor/ со всеми настройками (правила, команды, сценарии).

Куда размещать: все три пункта кладут в корень папки сайта — туда же, где лежат основные файлы проекта (index.html, wp-content, local, bitrix и т.п.).

Пример структуры:

site-project/
  AGENTS.md
  .cursorignore
  .cursor/
    rules/
    skills/
    commands/
    agents/
  index.html
  ...остальные файлы сайта...

После копирования в Cursor открывают именно эту папку через File → Open Folder. Если файлов нет — напишите руководителю, не собирайте настройки вручную.

Если уже есть опыт работы в Cursor и есть желание — файлы можно доработать под себя: добавить или изменить правила, команды и сценарии (skills). Главное — не ломать общие договорённости команды и не выкладывать в настройки секреты. Новичкам лучше сначала работать на готовом комплекте, а правки согласовывать с руководителем.

Что проверить сразу

  • В настройках агента лучше оставить подтверждение команд — программа не будет запускать команды без вашего согласия.
  • Не включайте режим автоматического выполнения всех команд без подтверждения на боевых проектах.
  • Убедитесь, что в корне проекта есть .cursorignore, AGENTS.md и папка .cursor/. Если чего-то нет — запросите у руководителя.

2. Интерфейс и горячие клавиши

Условно в Cursor три рабочие зоны:

  • слева — список файлов сайта;
  • в центре — код;
  • сбоку — чат с помощником.

Внизу иногда открывается терминал. Если помощник сам запускает команды, программа обычно спрашивает разрешение.

Готовые команды, правила и сценарии проекта смотрит руководитель в разделе Customize (боковая панель). Обычному сотруднику достаточно знать команды через / в чате.

Основные действия

Действие Как сделать
Открыть чат Ctrl + I (Mac: Cmd + I)
Новый чат кнопка New Chat
Переключить режим (Ask / Plan / Agent / Debug) Shift + Tab или выпадающий список вверху чата
Быстро поправить выделенный кусок выделить код → Ctrl + K → написать, что сделать
Отправить выделенный код в чат выделить код → Ctrl + L
Добавить файл в разговор написать @ и выбрать файл, либо перетащить файл в чат
Добавить скрин макета перетащить картинку в окно чата
Посмотреть, что изменилось в окне изменений: зелёным добавлено, красным удалено
Принять или отклонить правку Accept / Reject (не жмите Accept All, не просмотрев diff)
Откатить работу помощника Restore Checkpoint (это не git revert — откатывает только правки помощника в текущем чате)

В правом нижнем углу поля ввода есть индикатор контекста (кружок). Если он почти заполнен, лучше начать новый чат — иначе помощник начинает путаться.

Режимы чата

Режим Когда брать Пример
Ask Нужно спросить, ничего не меняя «Где стили шапки?»
Plan Задача большая, сначала нужен план «Перенести блок услуг на новый шаблон»
Agent Обычная работа: сделать правку «Сверстай блок отзывов»
Debug Что-то сломалось «На мобилке уезжает меню»

Практичное правило: неясно — Ask, большая переделка — Plan, обычная задача — Agent, баг — Debug.

В режиме Plan после согласования плана нажмите кнопку Build или напишите «делай».

3. Как ставить задачи

Как правильно заводить чаты

  • На одну задачу — один чат.
  • Новая тема — новый чат. Иначе помощник путает старый контекст с новым.
  • Сразу прикрепляйте нужные файлы через @ или перетаскиванием.
  • Прикрепляйте скрин макета, если верстаете блок.
  • Пишите задачу конкретно: что сделать, в каком файле, что нельзя трогать.
  • На простые задачи оставляйте модель Auto — не тратьте лимит зря.

Плохо:

почини сайт

Нормально:

В файле @index.html сверстай блок «Наши услуги» после секции hero. Используй текущие стили проекта. Адаптив: 320, 768, 1200. Новые библиотеки не подключай. Файлы и классы не выдумывай.

Если не знаете, где лежит нужный файл

Особенно на WordPress, Bitrix, Joomla и других CMS путь к шаблону не всегда очевиден. Сначала спросите в режиме Ask:

Где в этом проекте лежит шаблон шапки / блока «Услуги»? Ничего не меняй, только покажи файлы.

Когда файл найден — новый чат или тот же, но уже с @ на конкретный файл.

Контент-менеджерам

Cursor правит файлы проекта (HTML, шаблоны тем, PHP и т.д.). Если контент живёт только в админке CMS и не выведен в файлы — помощник его оттуда не возьмёт. В таком случае либо правите через админку, либо уточняете у разработчика, в каком шаблоне/файле лежит нужный блок.

4. Команды и роли

В чате можно вызвать готовую заготовку через слэш: / и имя команды. Это то, что вы вводите сами — не нужно каждый раз писать длинный текст.

У команды также есть сценарии (skills) — пошаговые инструкции для помощника. Они подключаются автоматически по смыслу задачи. Сотруднику достаточно знать команды; настраивает их руководитель.

Команды, которые используем

  • /verst-block — сверстать или поправить блок;
  • /content-update — заменить текст или картинку без поломки вёрстки;
  • /migrate-block — перенести блок или страницу;
  • /check-page — проверить страницу перед сдачей.

Как работать по ролям

Верстальщик

  1. Открыть папку сайта.
  2. Новый чат, режим Agent, модель Auto.
  3. Прикрепить страницу, стили и скрин макета.
  4. Вызвать /verst-block или описать задачу.
  5. Проверить diff и страницу в браузере.

Экономит время на типовых блоках, адаптиве, правках сетки, переносе разметки между страницами.

Контент-менеджер

  1. В Ask — узнать, в каком файле лежит нужный текст.
  2. В Agent — /content-update с указанием: структуру HTML и классы не менять.
  3. Проверить страницу глазами в браузере.

Меньше риска случайно сломать вёрстку при замене текстов и картинок.

Веб-разработчик

  1. Крупный перенос или доработка — Plan, потом Build.
  2. Реализация — Agent.
  3. Баг — Debug.
  4. Типовые процессы — команды и сценарии проекта.

Единые правила в проекте снижают разброс в коде между сотрудниками.

Кто настраивает правила и команды

Базовый комплект (AGENTS.md, .cursorignore, папка .cursor/) запрашиваем у руководителя и кладём в корень папки сайта.

Если у вас уже есть опыт и желание — можете доработать настройки под свою работу: создать нужные skills, команды (/...) и правила. Например, свой сценарий проверки адаптива или команда под типовую правку на ваших проектах.

Новичкам лучше начать с готового комплекта. Существенные изменения для всей команды лучше согласовать с руководителем, чтобы у всех оставался единый стиль работы.

5. Примеры работы

Пример 1. Сверстать блок (HTML/CSS)

/verst-block

Сверстай блок «Преимущества» по скрину.
Вставь в @index.html после секции hero.
Используй текущие стили и нейминг проекта.
Сделай 3 карточки: иконка, заголовок, текст.
Классы по БЭМ.
Адаптив:
- десктоп — 3 колонки
- планшет — 2 колонки
- мобилка — 1 колонка
Новые библиотеки не подключай.
Файлы и классы не выдумывай.
После правок напиши, что изменил и что проверить.

Уточнение, если что-то не так:

На ширине 375px у карточек маловаты отступы.
Сделай нормальные поля и одинаковую высоту карточек.
Остальное не трогай.

Пример 2. WordPress — правка шапки

Режим Ask:
Где в этой теме WordPress лежит шаблон шапки? Ничего не меняй.

После ответа — новый чат, Agent:
В @header.php поправь отступы в шапке на мобилке (375px).
Используй стили темы, новые библиотеки не подключай.
Структуру и классы не ломай. Файлы не выдумывай.

Пример 3. WooCommerce — карточка товара

Режим Ask:
Где в теме переопределён шаблон карточки товара WooCommerce?

После ответа — Agent:
В найденном шаблоне поправь отступы у блока цены на мобилке.
Минимальные правки. Не трогай логику корзины и checkout.

Пример 4. Bitrix — шаблон компонента

Режим Ask:
Где лежит шаблон компонента каталога в этом проекте Bitrix?

После ответа — Agent:
В шаблоне компонента поправь сетку карточек: на 768px — 2 колонки, на 320px — 1.
Используй БЭМ и стили текущего шаблона сайта.
Ядро Bitrix и /bitrix/ не трогай.

Пример 5. Tilda-экспорт — правка блока

В @index.html поправь блок «О компании» по скрину.
Не ломай служебные классы Tilda, которые нужны для анимаций.
Минимальные правки. Новые библиотеки не подключай.

Пример 6. Заменить контент

/content-update

В блоке «О компании» на @about.html:
1) замени заголовок на «О нашей студии»
2) замени текст на текст из @new-text.txt
3) картинку hero замени на @images/about-hero.webp
HTML-структуру и классы не меняй.
Если нового изображения нет в проекте — так и напиши.

Пример 7. Перенос страницы

Режим Plan.

/migrate-block

Нужно перенести страницу «Услуги» со старого сайта в текущий проект.
Старый код: @old/services.html
Сначала план по блокам.
Не копируй старый CSS слепом.
В новом проекте используй его сетку и БЭМ.
Ничего не придумывай: только реальные файлы источника и назначения.

Когда план устраивает — нажмите Build или напишите «делай».

Пример 8. Сломалось после правок

После последних изменений на главной пропали отступы у футера.
Найди причину в текущих файлах и исправь точечно.
Соседние блоки не ломай.

6. Чеклист перед сдачей

Перед тем как принять правки и отдать задачу:

  1. Посмотрите diff — что именно изменилось, нет ли лишних файлов.
  2. Не нажимайте Accept All, не просмотрев изменения — особенно в файлах CMS.
  3. Откройте страницу в браузере (локально или на тестовом/staging, если так принято в проекте).
  4. Проверьте мобильную ширину (хотя бы 375px) и десктоп.
  5. Убедитесь, что не сломались ссылки, картинки, формы, меню.
  6. На CMS-проектах — что не затронуты лишние шаблоны и конфиги.
  7. Перед заливкой на сервер — согласуйте с ответственным и проверьте git status, если проект в git.

Для быстрой проверки можно вызвать /check-page — помощник пройдётся по коду и укажет риски. Финальную проверку глазами всё равно делаете вы.

Чего не делать

  • Не править wp-config.php, dbconn.php, .env и другие файлы с доступами.
  • Не вставлять пароли, API-ключи и персональные данные клиентов в чат.
  • Не включать режим выполнения всех команд без подтверждения на боевых проектах.
  • Не править сразу на продакшене без бэкапа или отдельной ветки.
  • Не использовать Cursor для личных задач — лимит общий на команду.

Что программа не заменяет

  • Финальную проверку в браузере.
  • Понимание макета и требований клиента.
  • Ответственность за сдачу.

7. Частые ошибки и к кому обращаться

Если что-то пошло не так

Ситуация Что сделать
Помощник «не видит» файл Убедитесь, что открыта папка проекта (File → Open Folder), прикрепите файл через @
Тянет не туда, выдумывает файлы Новый чат, короче задача, явные ограничения «не выдумывай, только реальные файлы». Укажите @ на нужные файлы
Контекст переполнен, ответы стали странными Начните новый чат, прикрепите только нужные файлы
Сломалась вёрстка после правки Restore Checkpoint в чате или откат через git — что доступно в проекте
Закончился лимит Обратитесь к руководителю
Не знаете, какую модель выбрать Оставьте Auto; если не помогло — спросите руководителя
Не знаете, где лежит шаблон в CMS Режим Ask или спросите разработчика проекта

К кому обращаться

Вопрос К кому
Нет .cursorignore, AGENTS.md или папки .cursor/ Запросите готовый комплект у руководителя и положите в корень папки сайта
Доступы к аккаунту, лимиты, выбор моделей Руководитель
Настройка .cursor/, правил и команд в проекте Руководитель / техлид
Сложный баг CMS, интеграции, деплой Разработчик проекта
Где в проекте лежит нужный шаблон Разработчик проекта или Ask в Cursor

8. Для руководителя: настройка проекта

Этот раздел — для руководителя. Обычным сотрудникам достаточно запросить у него готовые файлы и положить их в корень проекта (см. раздел 1).

Шаблон настроек

Готовый пакет лежит в репозитории https://github.com/VictorShurko/cursor-web-team-config. Руководитель передаёт сотрудникам ссылку или кладёт файлы в репозиторий сайта. Копировать в корень папки сайта:

  • AGENTS.md
  • .cursorignore
  • папку .cursor/ целиком

Что уже входит в шаблон

Файл / папка Назначение
00-no-hallucinations Не выдумывать файлы, API, классы
01-process-ru Русский язык, план, минимальные правки
02-bem-modern-layout БЭМ, семантика, адаптив, доступность, чистый код
03-wordpress WordPress / WooCommerce
04-bitrix 1C-Bitrix
05-other-cms Tilda, MODX, Megagroup, Joomla, OpenCart, самопис
06-content-safe Безопасные контент-правки
skills + commands Сценарии и команды /verst-block, /content-update и др.
layout-reviewer Субагент-ревьюер вёрстки

Обязательные требования к коду (заложены в правилах)

  • БЭМ для новой и правимой вёрстки (если в проекте уже своя схема имён — следовать ей).
  • Семантическая вёрстка: header, nav, main, section, article, footer.
  • Базовая доступность: alt, focus, button/link по смыслу.
  • Адаптив: брейкпоинты проекта или ориентиры 320, 768, 1024, 1440.
  • Кроссбраузерность для современных браузеров.
  • Чистый код: без лишних библиотек, без мёртвого CSS/JS, без !important без причины.
  • Не выдумывать: ни файлов, ни классов, ни хуков, ни API плагинов.

Как внедрить в новый сайт

  1. Открыть папку сайта в Cursor.
  2. Скопировать файлы из шаблона в корень сайта.
  3. Открыть чат и написать: «Прочитай AGENTS.md и правила в .cursor/rules. Кратко подтверди, какая это CMS по файлам проекта. Ничего не меняй».
  4. Дальше команда работает через команды /verst-block, /content-update и т.д.

Hooks и MCP (для продвинутой настройки)

Hooks — автоматические скрипты после правок (lint, проверки). MCP — подключения к внешним системам (документация, Figma). На старте команды это не обязательно. Подключайте только то, чем реально пользуетесь.

Шаблон настроек: https://github.com/VictorShurko/cursor-web-team-config. Подробные шаги внедрения — в файле HOW-TO.md внутри репозитория.

Отдельная инструкция по переносу сайта: docs/site-migration-instruction.html, готовый промпт — docs/site-migration-prompt.md.
